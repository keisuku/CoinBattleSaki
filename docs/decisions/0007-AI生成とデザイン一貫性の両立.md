# ADR-0007: AI生成とデザイン一貫性の両立

## ステータス: 承認

## コンテキスト

CoinBattleSakiは個人開発 + AI開発体制で進行している。
キャラクター8体（＋チャイルドバリアント各5体 = 計48体）のビジュアルアセットが必要であり、
プロのアーティスト雇用は現段階では非現実的。AI画像生成の活用が前提となる。

しかしGDDでは以下の原則が明記されている:

> 「生成AIガチャでは到達不能。深い世界観 → デザイン力 → 画力 → 一貫性の順」

つまり**AIに「いい感じに作って」と投げるだけでは、SF2レベルのキャラデザインには到達できない**。
問題は「AIを使うかどうか」ではなく、**「AIをどう使えば一貫性のある商業品質のIPを構築できるか」**である。

### AI生成で一貫性が崩壊する具体的な原因

| 崩壊パターン | 具体例 | なぜ起きるか |
|-------------|--------|-------------|
| **スタイルドリフト** | 同じキャラでも生成ごとに画風が変わる | プロンプトの解釈が毎回微妙に異なる |
| **プロポーション不安定** | 頭身・体格・手の大きさが毎回変わる | 人体の構造的理解ではなく統計的近似で描画 |
| **配色の揺れ** | 「赤」のトーンが毎回違う | カラーコードではなく言語的「赤」で解釈 |
| **シルエット崩壊** | 特徴的なポーズ・衣装ディテールが消える | 画像ごとに独立して生成されるため構造記憶がない |
| **世界観の混濁** | キャラAはアニメ調、キャラBは写実的 | 統一された「世界」の概念がAIにない |
| **ディテール変異** | 装飾品・武器・紋章が毎回違う形になる | 細部の再現性が低い |

**核心**: AIは「1枚の絵を上手に描く」能力は高いが、「複数の絵の間の一貫性を保つ」能力が根本的に弱い。
一貫性は人間が設計し、AIは人間の設計に従って「画力」を提供する道具として使う。

---

## 決定: 「人間が骨格、AIが肉付け」の分業モデルを採用

### 基本原則

```
人間が決めること（=一貫性の源泉）:
  世界観 → キャラ設定 → シルエット → 配色 → ポーズ規定

AIが担うこと（=画力と量産力）:
  レンダリング → バリエーション展開 → 演出素材量産
```

GDDの原則「深い世界観 → デザイン力 → 画力 → 一貫性」に完全に従う:
- **深い世界観**: 人間が定義（ADR-0006では扱わない。課題#1の管轄）
- **デザイン力**: 人間がキャラクターデザインシート（CDS）を定義
- **画力**: AIが提供。CDSに基づいてレンダリング
- **一貫性**: CDSの厳格な運用 + SF2テストで検証

## レイヤー1: キャラクターデザインシート（CDS）— 人間が定義する「憲法」

### CDSとは
全キャラクターのビジュアル生成の前に、人間が作成する設計書。
**これがない状態でAI生成を始めてはいけない。**

### CDS必須項目

```yaml
# === キャラクターデザインシート (CDS) テンプレート ===

identity:
  name: "JOHN"
  codename: "The Flash Trader"
  archetype: "5分スキャルピング・順張り"

# --- シルエット定義（最重要） ---
silhouette:
  # 白黒シルエットで「誰か」がわかること
  body_type: "中肉中背・やや前傾姿勢"
  head_ratio: "7頭身"
  signature_shape: "両手にナイフ状の武器。常に前傾で走り出しそうな姿勢"
  silhouette_test: "影絵にしてもJOHNとわかるか？→ ナイフ+前傾で判別可能"

# --- カラーパレット（厳密なHEX指定） ---
colors:
  primary: "#1E90FF"      # ドジャーブルー（メインカラー60%）
  secondary: "#0A0A2E"    # ダークネイビー（サブカラー30%）
  accent: "#00FFFF"       # シアン（アクセント10%）
  skin: "#F5D6C3"         # 肌色
  hair: "#1C1C1C"         # 髪色
  # ※ AI生成時にこのHEXコードを厳守する

# --- 不変ディテール（これが変わったら別キャラ） ---
invariants:
  - "左目の下に小さな傷跡"
  - "両手のナイフは必ず逆手持ち"
  - "ジャケットの右肩に雷マークのエンブレム"
  - "ブーツは膝下まで"

# --- NG定義（AIがやりがちな逸脱を事前に封じる） ---
never:
  - "笑顔にしない（常にクールな表情）"
  - "ナイフを順手持ちにしない"
  - "髪を長くしない（常にショートカット）"
  - "筋肉質にしすぎない"

# --- ポーズバリエーション（許可リスト） ---
poses:
  idle: "やや前傾、両手ナイフを体側に下げている"
  attack: "右手ナイフで斜め上から切りつけ"
  defend: "両腕をクロスして防御"
  victory: "ナイフを右手で回転させながら背を向ける"
  defeat: "片膝をつき、ナイフを地面に突き刺す"
```

### CDS作成手順

1. **言語で定義** → 上記テンプレートを全キャラ分、文章で埋める
2. **ラフスケッチ** → 棒人間レベルでよい。シルエットとポーズの確認が目的
3. **AI生成でプロトタイプ** → CDSに基づいて初回生成（10枚以上）
4. **取捨選択** → CDSに最も忠実な1枚を「リファレンス画像」に決定
5. **CDSを更新** → リファレンス画像を見てCDSの曖昧な箇所を修正
6. **ロック** → CDS v1.0としてフリーズ。以降の生成は全てこのCDSに従う

## レイヤー2: AI生成ワークフロー — CDSに基づく制御された生成

### ツール選定方針（2026年時点）

| 用途 | 推奨ツール | 理由 |
|------|-----------|------|
| **キャラ初期コンセプト** | Midjourney / DALL-E 3 / Stable Diffusion | 多様なコンセプトを高速に探索 |
| **一貫性のあるバリエーション** | ComfyUI + IP-Adapter + ControlNet | リファレンス画像からポーズ違いを安定生成 |
| **LoRA（キャラ固定）** | Stable Diffusion + LoRA微調整 | 1キャラあたり20-30枚の学習でスタイル固定 |
| **ドット絵変換** | Aseprite + AI補助 | ゲーム内で使うピクセルアートへの変換 |
| **背景・環境** | Midjourney / Flux | キャラより一貫性要件が緩い |
| **エフェクト・演出** | After Effects + AI動画ツール | パチンコ的演出のエフェクト素材 |

### 生成ワークフロー

```
Phase A: コンセプト探索（CDS作成前）
  ├── 世界観キーワードでAI生成を大量に回す（100枚〜）
  ├── 「方向性として良い」ものを人間がピックアップ
  └── CDS作成のインプットにする
      ※ この段階の画像は全て捨てる（最終アセットには使わない）

Phase B: リファレンス確立（CDS v1.0作成後）
  ├── CDSに基づいてプロンプトを構築
  ├── 10枚生成 → CDSとの一致度を人間が採点
  ├── 最高スコアの1枚を「公式リファレンス」に決定
  ├── リファレンス画像を元にLoRAを訓練（任意）
  └── IP-Adapter用のリファレンスセットを構築（正面/横/背面）

Phase C: アセット量産（リファレンス確立後）
  ├── IP-Adapter + ControlNet でポーズバリエーション生成
  ├── 各生成物をCDSチェックリストで検証
  ├── 不合格 → 再生成 or 手動修正
  └── 合格 → アセットライブラリに登録

Phase D: チャイルドバリアント展開
  ├── マザーBotのCDSをベースに差分定義
  │   例: JOHN_agg = 「JOHNのCDS + 目が赤い + 傷跡が増える + 前傾がさらに深い」
  ├── 差分が小さいため、LoRA/IP-Adapterで高い一貫性を維持可能
  └── 48体全てを個別に0からデザインする必要はない
```

### プロンプトエンジニアリングのルール

```
# 構造化プロンプトテンプレート

[スタイル指定]
dark underground battle game art style, consistent with CoinBattleSaki universe,
{CDS.colors.primary} as dominant color,

[キャラ指定]
{CDS.identity.name}, {CDS.silhouette.body_type}, {CDS.silhouette.head_ratio},
{CDS.silhouette.signature_shape},

[不変ディテール]
{CDS.invariants を全て列挙},

[ポーズ]
{CDS.poses.{target_pose}},

[NG]
NOT: {CDS.never を全て列挙},

[技術指定]
high quality, detailed, anime-influenced style, dark palette
```

**鉄則**: プロンプトを「なんとなく」で書かない。CDSから機械的に組み立てる。

## レイヤー3: 品質ゲート — SF2テスト

全キャラクターのビジュアルアセットは、以下の5つのテストに合格しなければリリースしない。

### テスト1: シルエットテスト
```
方法: キャラ画像を真っ黒に塗りつぶす（シルエット化）
基準: シルエットだけで8体全員を区別できるか？
不合格例: JOHNとMIKEのシルエットが似すぎている
→ CDSのsignature_shapeを見直す
```

### テスト2: カラーテスト
```
方法: キャラ画像をぼかして色の塊にする（5pxガウスぼかし）
基準: 色の塊だけで8体全員を区別できるか？
不合格例: JOHNの青とDELTAのオレンジは区別できるが、
          YUKIの白とATRの水色が混同される
→ カラーパレットを再調整
```

### テスト3: サムネイルテスト
```
方法: キャラ画像を32x32ピクセルに縮小する
基準: 32x32でも「誰か」がわかるか？
不合格例: 縮小すると全員同じに見える
→ シルエットの差別化が不足
```

### テスト4: 「別ゲー」テスト
```
方法: 8体を並べて俯瞰する
基準: 全員が「全く違う方向性のキャラ」に見えるか？
       同時に、「同じ世界に存在する」一貫性があるか？
不合格例: 全員がサイバーパンク風で差別化不足
→ アーキタイプ（体格・武器・姿勢）の多様性を見直す
```

### テスト5: 一貫性テスト（AI生成固有）
```
方法: 同一キャラの異なるポーズ/場面の画像を5枚並べる
基準: 5枚全てが「同一人物」に見えるか？
不合格例: ポーズが変わると顔つきや服装が変わっている
→ LoRA/IP-Adapterの調整、またはCDSのinvariantsを強化
```

## レイヤー4: アセット管理 — バージョン管理と命名規則

### ディレクトリ構成

```
assets/
├── cds/                          # キャラクターデザインシート
│   ├── john.yaml
│   ├── mike.yaml
│   ├── ...
│   └── _template.yaml
├── references/                   # 公式リファレンス画像（ロック済み）
│   ├── john/
│   │   ├── john_front_v1.png
│   │   ├── john_side_v1.png
│   │   └── john_back_v1.png
│   ├── mike/
│   └── ...
├── variants/                     # チャイルドバリアント
│   ├── john_agg/
│   ├── john_con/
│   └── ...
├── game/                         # ゲーム内使用アセット（最終成果物）
│   ├── sprites/
│   ├── portraits/
│   └── effects/
├── prompts/                      # 生成に使用したプロンプトログ
│   └── john_idle_20260309.txt
└── rejected/                     # 不合格になった生成物（学習用に保存）
    └── john_rejected_001.png
```

### 命名規則

```
{キャラID}_{ポーズ}_{バージョン}.{拡張子}
例: john_idle_v1.png
    john_attack_v2.png
    john_agg_idle_v1.png  （チャイルドバリアント）
```

### バージョン管理ルール
- CDSファイル（.yaml）はGitで管理する
- リファレンス画像はGit LFSで管理する
- 生成プロンプトは必ずログとして保存する（再現性の確保）
- 不合格画像も `rejected/` に保存する（何がダメだったかの記録）

## レイヤー5: フェーズ別AI活用戦略

### Phase 0（現在）: コンセプト検証

| やること | AI活用度 | 成果物 |
|---------|---------|--------|
| 世界観のビジュアルムードボード作成 | 高（AI大量生成→人間が選別） | ムードボード画像10-20枚 |
| 8体のシルエット差別化の検証 | 低（人間がラフスケッチ） | 棒人間レベルのシルエット |
| カラーパレットの決定 | 低（人間が配色設計） | 8色パレット表 |
| 「このキャラを推したいか？」のSNS検証 | 高（AI生成画像で人気投票） | SNSでの反応データ |

**Phase 0ではCDSの「骨格」を固めることが目標。AI生成の品質は問わない。**

### Phase 1（MVP）: 最低限のアセット

| やること | AI活用度 | 成果物 |
|---------|---------|--------|
| CDS v1.0の完成 | 低（人間が定義） | 8キャラ分のCDS |
| 公式リファレンス画像 | 中（AI生成→人間が選別・修正） | 正面/横/背面 × 8体 |
| ゲーム内ポートレート | 中（AI生成→人間がレタッチ） | 8枚 |
| バトル中のスプライト | 低〜中（ドット絵ならAseprite手作業の方が一貫性高い） | 基本ポーズ × 8体 |

### Phase 2以降: IP品質への引き上げ

- 成功の兆しが見えたら、**CDSを元にプロのアーティストに発注**する選択肢も開ける
- CDSが「設計書」として機能するため、アーティストへの指示書としてそのまま使える
- AI生成 → プロアーティスト への移行がスムーズ

## リスク評価

### 法的リスク

| リスク | 深刻度 | 対策 |
|--------|--------|------|
| AI生成画像の著作権帰属が不明確 | 中 | 日本では「AI生成物に著作権なし」が現状の解釈。ただし「人間の創作的寄与」が認められればIP保護の余地あり。CDSによる詳細な設計指示が「創作的寄与」の根拠になる |
| 既存作品との類似性 | 中 | 生成時に特定の作品名・アーティスト名をプロンプトに含めない。類似チェックを人間が実施 |
| 商用利用ライセンス | 低 | Midjourney Pro / DALL-E / Stable Diffusion OSSはいずれも商用利用可能なライセンス体系 |

### 技術的リスク

| リスク | 深刻度 | 対策 |
|--------|--------|------|
| AIツールの仕様変更・廃止 | 中 | CDSとリファレンス画像が資産。ツールが変わっても再生成可能 |
| 一貫性の経年劣化 | 中 | 新しいアセットを追加するたびにSF2テスト5項目を実施 |
| LoRAモデルの陳腐化 | 低 | リファレンス画像があれば再訓練可能 |

### 戦略的リスク

| リスク | 深刻度 | 対策 |
|--------|--------|------|
| 「AI生成っぽさ」がユーザーに見透かされる | 高 | **これが最大のリスク**。対策は下記 |

#### 「AI生成っぽさ」の排除戦略

1. **ドット絵スタイルの採用を検討**: ピクセルアートはAI生成の「不気味の谷」を回避しやすい。
   SF2自体がドット絵。原点回帰として合理的。AI生成をベースにしてもピクセル化で均質化される
2. **限定的な手作業レタッチ**: 顔と手だけは人間が修正する。この2箇所がAI生成の違和感の主原因
3. **スタイルの割り切り**: 「超リアル」を目指すとAI生成の粗が目立つ。
   意図的にスタイライズド（デフォルメ・アニメ調）に振ることで、一貫性を保ちやすくする
4. **演出で勝負**: 静止画の品質よりも、パチンコ的演出の動きとタイミングで体験価値を作る。
   「絵がすごい」ではなく「演出がすごい」で勝つ

## 代替案

### 案A: 全てプロのアーティストに発注
- メリット: 最高品質の一貫性
- デメリット: Phase 0の予算ゼロに反する。8体×複数ポーズ = 数十万〜数百万円
- 判定: **Phase 0-1では却下。Phase 2以降で再検討**

### 案B: AI生成をそのまま使う（品質管理なし）
- メリット: 最速・最低コスト
- デメリット: GDDが警告する「生成AIガチャ」そのもの。IP価値がゼロ
- 判定: **却下**

### 案C: 既存のフリー素材・アセットストアを利用
- メリット: 一貫性のあるアセットパックが存在する
- デメリット: CoinBattleSaki固有のキャラクター性が出ない。IP展開不可
- 判定: **プレースホルダーとしては可。最終アセットとしては却下**

### 案D: 本ADRの方針（CDSベースのAI活用） ← 採用
- メリット: コストゼロ〜最小で一貫性を追求。CDSが資産として残る
- デメリット: プロアーティストには及ばない。CDS作成に時間がかかる
- 判定: **Phase 0-1の最適解。成功したらPhase 2でプロ発注に切り替え可能**

## まとめ: 5つの鉄則

1. **CDSなしにAI生成を始めるな** — 「とりあえず生成」は一貫性崩壊の始まり
2. **人間が骨格、AIが肉付け** — シルエット・配色・不変ディテールは人間が決める
3. **SF2テストを毎回やれ** — 5つのテストに合格しないアセットはリリースしない
4. **プロンプトはCDSから機械的に組み立てろ** — 「いい感じに」は禁句
5. **逃げ道を用意しろ** — CDSがあればプロアーティストへの発注書にもなる
