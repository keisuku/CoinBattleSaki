# ADR-0002: 技術スタック選定

## ステータス: 廃止（Superseded by ADR-0005）

> **注意**: Bot内蔵型・サーバーゼロアーキテクチャの採用（ADR-0005）により、
> このADRで提案されたNext.js + Phaser + サーバー構成は無効となりました。
> プラットフォーム（Web / モバイルアプリ）および技術スタックは再選定が必要です。

## コンテキスト
個人開発+AIで、格闘ゲーム風UI + リアルタイム市場データ連動のWebアプリを構築する。
メディアミックス展開を最終目標とし、まずはブラウザで動くMVPを作る。

## 決定
以下の技術スタックを採用する:

### フロントエンド
- **TypeScript**: 型安全性（金融データの型定義が重要）
- **Next.js 14+ (App Router)**: SSR/SSG、API Routes、Vercelデプロイ
- **Phaser 3**: 格闘ゲームのバトル画面（2Dゲームエンジン）
- **TailwindCSS**: UIコンポーネントのスタイリング
- **Framer Motion**: UI遷移アニメーション

### バックエンド（Phase 1は最小限）
- **Next.js API Routes**: 軽量なAPIエンドポイント
- **WebSocket (ws)**: リアルタイム市場データ配信

### データ
- **SQLite (better-sqlite3)**: Phase 1のローカルDB
- **PostgreSQL**: Phase 2以降で移行

### インフラ
- **Vercel**: フロントエンド + API Routes
- **Railway**: WebSocketサーバー（Vercelはlong-lived接続非対応のため）

## 理由

### Next.js を選んだ理由
- React生態系のフル活用（コンポーネント資産が豊富）
- API RoutesでBFFが簡単に構築可能
- Vercelでゼロコンフィグデプロイ
- 個人開発での生産性が最も高い
- Claude Code / AI支援との相性が良い（コード生成のベースが豊富）

### Phaser 3 を選んだ理由
- Web上の2Dゲームエンジンとして最も実績あり
- TypeScript対応
- スプライトアニメーション、物理演算、入力ハンドリングが充実
- React内に埋め込み可能（PhaserをCanvas内で動かす）
- PixiJSより格闘ゲーム向けの機能が豊富

### Unity WebGL を見送った理由
- ビルドサイズが大きい（初回ロードが遅い）
- Web向けの制約が多い（WebSocket、DOM操作等）
- 学習コストが高く、個人+AI開発では生産性が下がる
- Claude CodeでのC#支援よりTypeScript支援の方が質が高い

## リスク
- Phaser 3 は大規模化すると管理が難しくなる（Phase 3以降で再検討）
- Vercel + Railway の2サービス運用の複雑さ
- SQLite→PostgreSQL移行時のマイグレーション作業

## 代替案
- **PixiJS**: Phaserより軽量だが、ゲーム用機能が少ない
- **Unity WebGL**: リッチだが重い。モバイル展開時に再検討
- **Godot (Web export)**: 軽量だがエコシステムが小さい
