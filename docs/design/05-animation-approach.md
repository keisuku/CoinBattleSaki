# 設計課題 #5: 安っぽくないアニメーション/映像制作アプローチ

## 前提

ブラウザベースのコインバトルゲームにおいて、限られたリソースで「安っぽく見えない」映像体験を実現する。
フル3DやフルアニメーションのAAAタイトルと張り合うのではなく、**意図的なスタイル選択**によって品質感を出す。

---

## 1. 「安っぽさ」の正体 — 避けるべきパターン

| 安っぽく見える要因 | 具体例 | 根本原因 |
|---|---|---|
| 動きの均一性 | 全てが同じ速度で動く | イージングの欠如 |
| 素材の浮き | キャラとUIと背景がバラバラの質感 | アートディレクション不在 |
| タイミングの悪さ | ヒット演出が0.5秒遅れる | フィードバックループの設計不足 |
| エフェクトの薄さ | パーティクルが2〜3個飛ぶだけ | レイヤリング不足 |
| 解像度の不統一 | 一部だけピクセルが荒い | アセット管理の問題 |

**核心**: 安っぽさは「予算の少なさ」ではなく「設計の甘さ」から生まれる。

---

## 2. 推奨アプローチ: レイヤードモーション戦略

### 2.1 基本思想

```
「1つの高品質アニメーション」より「3つの簡素なレイヤーの重ね合わせ」
```

人間の目は単体の動きの品質より、**複数要素が連動して動く協調性**に品質感を感じる。

### 2.2 レイヤー構成

```
Layer 4: UI フィードバック（数字、ゲージ、テキスト）
Layer 3: エフェクト（パーティクル、フラッシュ、シェイク）
Layer 2: キャラクター（ポーズ変化、表情）
Layer 1: 背景（環境変化、カメラワーク）
```

**例: コイン投げ → 攻撃ヒットの演出**

| 時間 | Layer 1 背景 | Layer 2 キャラ | Layer 3 エフェクト | Layer 4 UI |
|---|---|---|---|---|
| 0ms | — | コイン投げモーション開始 | — | — |
| 200ms | 微かにズームイン | コインが回転 | コインに光の軌跡 | — |
| 500ms | — | コイン結果表示 | フラッシュ | 結果テキスト表示 |
| 600ms | 画面シェイク(2fr) | 攻撃ポーズ | ヒットエフェクト放射 | ダメージ数字ポップ |
| 800ms | 色調変化(戻り) | 待機ポーズへ | パーティクル減衰 | 数字フェードアウト |

## 3. 具体的な技術選択肢の比較

### 3.1 キャラクター表現

| 方式 | 品質感 | 制作コスト | 拡張性 | 推奨度 |
|---|---|---|---|---|
| **A. Live2D風パーツアニメ** | ★★★★ | 中 | 中 | ◎ |
| B. スプライトシートアニメ | ★★★ | 高(枚数依存) | 低 | ○ |
| C. CSS/SVGトゥイーン | ★★ | 低 | 高 | △ |
| D. フル3D (Three.js) | ★★★★★ | 極高 | 高 | × (スコープ外) |

#### 推奨: A. パーツ分割 + トゥイーンアニメーション

```
キャラクターを5〜8パーツに分割:
  - 頭部（表情差分はテクスチャ切替）
  - 胴体
  - 左腕 / 右腕
  - 左脚 / 右脚（立ち絵の場合は省略可）
  - 装飾品（髪飾り、武器など）

各パーツに対して回転・移動・スケールのトゥイーンを適用
→ 少ない素材で滑らかな動きを実現
```

**利点**:
- 1枚の高品質イラストから複数アニメーションを生成可能
- 表情差分はテクスチャスワップで対応（描き下ろし最小限）
- Spine / DragonBones 等のツールが使える（ただしライセンス確認要）

### 3.2 エフェクト表現

| 方式 | 適用箇所 | 実装 |
|---|---|---|
| **CSS Animation** | UI遷移、テキスト演出 | transform + opacity + filter |
| **Canvas 2D パーティクル** | ヒットエフェクト、コイン演出 | 自前の軽量パーティクルシステム |
| **WebGL シェーダー** | 画面全体の色調変化、歪み | ポストエフェクト限定で使用 |
| **Lottie (After Effects)** | 定型演出（勝利、レベルアップ） | JSON アニメーション再生 |

#### 推奨: CSS + Canvas 2D を基本、要所で Lottie

```
日常的な演出 → CSS Animation（軽量・メンテ容易）
バトル演出   → Canvas 2D パーティクル（自由度高い）
特別演出     → Lottie（デザイナーが After Effects で制作）
```

### 3.3 カメラワーク・画面演出

安っぽさを一番簡単に消せるのが**画面全体の微細な動き**。

```css
/* 例: ヒット時の画面シェイク */
@keyframes hit-shake {
  0%   { transform: translate(0, 0); }
  25%  { transform: translate(-4px, 2px); }
  50%  { transform: translate(3px, -3px); }
  75%  { transform: translate(-2px, 1px); }
  100% { transform: translate(0, 0); }
}

/* 例: 緊張感を出すズーム */
@keyframes tension-zoom {
  0%   { transform: scale(1.0); }
  100% { transform: scale(1.05); }
}
```

**演出テクニック集**:

| テクニック | 効果 | コスト |
|---|---|---|
| 画面シェイク (2-4フレーム) | インパクト感 | 極低 |
| スローモーション (time-scale変更) | 決定的瞬間の強調 | 低 |
| ビネット (画面端を暗く) | 集中・緊迫感 | 低 |
| 色収差 (RGB分離) | ダメージ・異常状態 | 低 |
| 放射ブラー | スピード感 | 中 |
| 画面フラッシュ (白/対属性色) | ヒット確認 | 極低 |

## 4. サウンドとの連動（視聴覚の統合）

アニメーションの品質感の30〜40%は**音との同期精度**で決まる。

### 4.1 原則

```
映像が先、音が後 → 安っぽい
音と映像が同時  → 普通
音がわずかに先(1-2fr) → 高品質に感じる
```

### 4.2 実装指針

- Web Audio API でフレーム単位のタイミング制御
- `requestAnimationFrame` のタイムスタンプと音声再生を同一タイムラインで管理
- SE は「予備音(anticipation)」→「衝撃音(impact)」→「余韻(tail)」の3構造

```
コインヒット例:
  -100ms  「シュッ」（予備動作音）
    0ms   「ガキン！」（衝撃音） ← ヒットエフェクトと同期
  +200ms  「キーン...」（余韻） ← パーティクル減衰と同期
```

## 5. アニメーション設計原則 (12 Principles の応用)

ディズニーのアニメーション12原則から、ゲームUIに特に重要な6つ:

| 原則 | ゲームでの適用 | 具体例 |
|---|---|---|
| **Anticipation (予備動作)** | アクション前の「溜め」 | 攻撃前にキャラが少し後ろに引く |
| **Follow Through (後追い)** | 動きの余韻 | ダメージ数字が上に飛んでから落ちる |
| **Ease In/Out** | 等速運動の排除 | 全てのtransitionにcubic-bezierを設定 |
| **Squash & Stretch** | 弾力表現 | コインが着地時に潰れて跳ねる |
| **Staging (演出配置)** | 視線誘導 | 重要な演出時に他要素を暗くする |
| **Timing** | 間の取り方 | 決定打の前に0.3秒の「間」を入れる |

### Ease カーブの統一規格

```javascript
// プロジェクト共通イージング定義
const EASING = {
  // UI遷移用（落ち着いた動き）
  standard:  'cubic-bezier(0.4, 0.0, 0.2, 1.0)',
  // 登場演出（弾むように出現）
  enter:     'cubic-bezier(0.0, 0.0, 0.2, 1.0)',
  // 退場演出（素早く消える）
  exit:      'cubic-bezier(0.4, 0.0, 1.0, 1.0)',
  // バトル演出（鋭いアクション）
  impact:    'cubic-bezier(0.0, 0.0, 0.0, 1.0)',
  // バウンス（コイン跳ね）
  bounce:    'cubic-bezier(0.34, 1.56, 0.64, 1.0)',
};
```

## 6. パフォーマンス制約と最適化

### 6.1 バジェット設計

```
目標: 60fps 維持（最低30fps保証）
フレームバジェット: 16.6ms/frame

割り当て:
  ゲームロジック     : 2ms
  アニメーション更新  : 4ms
  パーティクル計算   : 3ms
  描画 (DOM/Canvas)  : 5ms
  バッファ           : 2.6ms
```

### 6.2 最適化ルール

1. **DOM アニメーションは `transform` と `opacity` のみ** — Layout/Paint を発生させない
2. **パーティクル上限は同時100個** — オブジェクトプールで再利用
3. **`will-change` は演出開始直前にセット、終了後に解除**
4. **モバイルではエフェクト品質を自動低減** — `navigator.hardwareConcurrency` で判定

## 7. 制作パイプライン

```
[デザイン指示書]
    ↓
[イラスト制作] → パーツ分割PSD/AI
    ↓
[アニメーション定義] → JSONタイムライン or Spine/DragonBones
    ↓
[エフェクト定義] → パーティクルパラメータ + Lottie JSON
    ↓
[サウンド同期] → タイムライン上にSEマーカー配置
    ↓
[統合・調整] → ブラウザ上でタイミング微調整
```

## 9. 判断が必要な項目

| # | 論点 | 選択肢 | 判断基準 |
|---|---|---|---|
| 9.1 | キャラアニメーションツール | Spine / DragonBones / 自前実装 | ライセンスコストとチーム習熟度 |
| 9.2 | Lottie の採用範囲 | 全演出 / 特別演出のみ / 不採用 | デザイナーのAE習熟度 |
| 9.3 | Canvas vs WebGL | Canvas 2D基本 / WebGL基本 | 対象端末の性能帯 |
| 9.4 | アニメーション定義形式 | JSON自前形式 / 既存ツール形式 | ツール依存度とメンテ性のバランス |
| 9.5 | モバイルの品質段階 | 2段階(高/低) / 3段階 / 自動調整 | QA工数との兼ね合い |

## 10. まとめ — 3つの鉄則

> **鉄則1: 動きを重ねろ**
> 1つのリッチなアニメーションより、3つのシンプルなレイヤーの同時再生。
>
> **鉄則2: 音と合わせろ**
> 視覚演出の品質感の4割は聴覚との同期で決まる。
>
> **鉄則3: 間を作れ**
> 予備動作→アクション→余韻。この3拍子がないと全てが安っぽくなる。
